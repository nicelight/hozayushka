## Findings

### TD-REPO-001 — Production weather path is permanently fixture-backed

- **Severity:** `HIGH`
- **Evidence:** The production tree has only the deterministic
  `RedactedWeatherFixtureAdapter` implementation of `WeatherProvider`, explicitly
  documented as never making a network request
  (`app/src/main/kotlin/com/hozayushka/app/adapters/weather/WeatherProviderAdapter.kt:100-121`).
  The production composition root wires that adapter unconditionally
  (`app/src/main/kotlin/com/hozayushka/app/app/FoundationRuntime.kt:64-70`),
  while launch and scheduled refreshes call the normal Weather Context path
  (`FoundationRuntime.kt:31-40,108-118`). The manifest requests only
  `ACCESS_NETWORK_STATE` and has no `INTERNET` permission
  (`app/src/main/AndroidManifest.xml:2-5`).
- **Impact:** The stored user API key, selected coordinates, 30-minute refresh,
  provider failures and Yandex response mapping cannot affect the installed
  production path; it always returns the fixed fixture payload. This leaves the
  accepted Weather Provider boundary and the weather portions of FT-002/FT-008
  unexercisable in production and makes future weather fixes depend on
  a wiring replacement rather than the existing seam.
- **Smallest remediation direction:** Implement or select the real Yandex
  adapter behind the existing `WeatherProvider` contract, wire it for the
  product composition root, and retain `RedactedWeatherFixtureAdapter` only in
  explicit probe/test wiring. Add the minimum network transport/permission
  required by that accepted provider boundary while preserving the local-key
  and redaction contract. If this checkout is intentionally still
  foundation-only, explicitly classify the product weather claims as deferred
  instead of leaving the fixture silently production-wired.
- **Uncertainty:** The `0.1-foundation` version and Foundation probe route show
  that fixture-only behavior was once intentional. The current feature docs and
  Yandex contract describe product weather as implemented/accepted, so the
  present production wiring is debt unless the owner confirms that this is still
  a foundation-only release.

### TD-REPO-002 — Main and forecast surfaces rebuild UI and decode state at 20 Hz

- **Severity:** `MEDIUM`
- **Evidence:** Main Display schedules `refresh()` every 50 ms
  (`app/src/main/kotlin/com/hozayushka/app/display/DisplayCapability.kt:654-669`).
  Each refresh reloads the persisted weather record through
  `weather.projection()` (`DisplayCapability.kt:576-652`; 
  `app/src/main/kotlin/com/hozayushka/app/weather/WeatherCapability.kt:372-438`),
  where the SharedPreferences store reparses daily/history/hourly serialized
  strings (`WeatherCapability.kt:98-135`), then removes and recreates all four
  card view trees (`DisplayCapability.kt:631-646`). Forecast screens repeat the
  same whole-grid rebuild every 50 ms for 8/10 cards
  (`DisplayCapability.kt:718-744,790-809`). The main ticker is also posted both
  unconditionally and from `onViewAttachedToWindow` (`DisplayCapability.kt:660-669`),
  which can create two concurrent 50 ms chains on initial attach.
- **Impact:** This is a confirmed high-churn mechanism: repeated persistence
  decoding, list/trend allocations, `GradientDrawable`/`TextView` creation and
  listener reattachment occur on the Android main thread even while weather and
  forecast data are unchanged. On the deferred low-end target this can consume
  frame/GC budget and make touch/timer behavior more sensitive; it also couples
  every touch-routing change to recreated card instances. The duplicate startup
  scheduling can multiply that work.
- **Smallest remediation direction:** First make ticker ownership single-source
  by removing the duplicate startup post or guarding it. Then retain card/grid
  view instances and update only clock/countdown/overdue values at the required
  cadence; rebuild weather/preset/forecast subtrees only when their projection
  or Settings state changes. Measure the target route after the minimal change
  before adding any broader UI framework or caching layer.
- **Uncertainty:** No profiler or Samsung/custom-ROM run is available; the
  target-device evidence is explicitly deferred. Current generic-emulator
  screenshots and passing host/build checks do not prove visible jank, so this
  is a material optimization/maintenance debt, not a confirmed runtime
  performance failure or a standalone release blocker.
